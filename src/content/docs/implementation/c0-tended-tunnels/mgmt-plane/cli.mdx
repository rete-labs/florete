## CLI Surface

Two binaries, split by audience:

- **`retectl`** — **operator-facing; present on every install, used from the operator's workstation**. Authors rete state: CA operations, validation, compilation, bundle issuance. Never touches a running agent. It ships everywhere because [artifact composition](../../installer#artifact-composition) is a set, not a per-role subset — a node that never runs it is the cost of keeping placement a config fact — but the operator's workstation is where it is *used*.
- **`flor`** — **every node**. The daemon plus the node-local user CLI: enrollment, apply, status. One binary serves end users, server admins, and the system service.

This matches the author-vs-participant split used by `kubectl`/`kubelet`, `terraform`/agent, and similar tooling — and the names mirror the layer each acts on: **`retectl` administers the rete** (the trust domain — not any single `flor`, and not one Coordinator), while **`flor` is the node agent**, exactly as `kubectl` administers the cluster and `kubelet` runs on the node. The `-ctl` suffix names the thing controlled (the rete), which is why it is not `florctl`: the tool never controls a `flor`, it authors rete state. An end user installing Florete on their laptop gets `flor` with a small, focused command set and simply never reaches for `retectl`, which is present but not theirs to use; operators use it on their own machine for rete-authoring work.

**Both binaries share the same output rules, and differ on one** ([Installer § Logging](../../installer#logging)). User messages go to **stderr**, written for the person who typed the command; stdout carries a command's *data* and nothing else, so `flor agent status | jq` stays meaningful. Where they part is the **log stream**, which exists for processes nobody is watching:

- **`flor`'s commands and daemon log to syslog.** They change *host* state an admin may have to reconstruct later — `install`, `uninstall`, `enroll`, `agent enable`/`disable` — and the daemon has no terminal at all. `--log-stderr` redirects the stream, with `FLOR_LOG_DESTINATION` and `[log] destination` in `config.toml` as its environment and file forms; `RUST_LOG` raises the level, which defaults to `error` for commands and `info` for the daemon. A command that asks another process to act does not log, so `flor agent sync` is silent and the daemon records the sync it ran.
- **`retectl` has no syslog destination.** Its stream defaults to **stderr and to off**, and `RUST_LOG` turns it on. It changes *rete* state — whose record is the git commit — and operator-local material, and the person who ran it is watching the terminal. With `RUST_LOG` set a failure appears twice, once as a user message and once as a log record; that is correct for a stream someone deliberately switched on.

`retectl` reads none of flor's configuration, and exactly one of its locations: `agent.sock`, needed by `publish` alone.

### retectl (operator, authoring)

```
retectl init <rete-name>                    # once per rete, inside a fresh repo: scaffold
                                            # the YAML collections, mint the root CA and
                                            # the management-plane/mgmt-signer, write
                                            # the operator tree's rete.json naming the
                                            # trust domain, and write retectl's own
                                            # config template for this rete. The only
                                            # way a root CA comes into existence.
retectl id issue --kind <management-plane|control-plane>
                 --name <name>              # mint a keypair that stays in the operator's
                                            # custody and sign its cert. Signing kinds
                                            # only: a TLS key issued here would have
                                            # nowhere to go. This is how a mgmt signer is
                                            # rotated — the compiler signs artifacts with
                                            # the key it produces.
retectl issue-bundle --node <node-name>
                                            # pack the per-node enrollment bundle from
                                            # the committed compiled tree: trust anchors,
                                            # the node identity, and every workload
                                            # identity (users/services) YAML places on
                                            # this node, plus that node's artifact set.
                                            # Compiles nothing, and refuses when the
                                            # compiled tree is not committed. Needs no
                                            # coordinator and no network at all.
                                            # Flow A only in C0.
                                            # Always writes <repo>/bundles/<node>.bundle.

retectl validate                            # schema + cross-ref + access consistency
retectl compile                             # compile the rete; always writes
                                            # <repo>/.flor/compiled/
retectl publish                             # push compiled artifacts to the rete
                                            # coordinator (see Coordinator). No target
                                            # argument: coordinator-publisher is a
                                            # reserved service name, so the destination
                                            # follows from it and rete.name
```

Notes:

- **Source discovery.** The repo root is found by walking up from the working directory to `rete.yaml`, never named by a flag; outside a repo every command refuses. Then recursively glob `*.yaml`/`*.yml` under that root (skipping `.flor/`, `bundles/`, dotfiles; honoring `include`/`exclude` in `rete.yaml`), then merge same-kind collections into one whole-view before compiling. File layout is operator-chosen — see [Source Layout](../source-layout). There is no per-invocation file override: narrowing which files form the rete is `source.include`/`source.exclude` in `rete.yaml`, which is committed and reviewable, and a flag that selected a different set per run would be a second discovery rule with no repo root to anchor it.
- **`retectl` runs inside a rete repository or not at all** — it walks up from the working directory to find `rete.yaml`, as git finds `.git`, and refuses outside one. `retectl init` is the one exception and has to be: it is what *creates* `rete.yaml`, so it refuses when the walk-up succeeds instead — and it **requires a git repository**, refusing outside one, since the compiled tree's commit state is what `issue-bundle` gates on ([Enrollment § Decision Log](../enrollment#decision-log), ENRL-C0-35). The scope, the paths and the rete's name all follow from that, so no command carries a `--rete` flag to say which rete it means — and none carries an output path either: `compile` always writes `<repo>/.flor/compiled/` and `issue-bundle` always writes `<repo>/bundles/<node>.bundle`. The compiled tree is an *input* to the next compile, being the version ledger, so redirecting it elsewhere produces a tree that compiles from the wrong history.
- **Operator-held material lives in `retectl`'s own tree**, `~/.retectl` (overridden whole by `RETECTL_HOME`), never in the repository: one identity store per rete at `retes/<scope>/identity/`, holding the root CA at `authorities/root.crt|.key`, the signers at `principals/<name>.crt|.key`, and `rete.json` naming the trust domain — the same store shape a node uses, with different parts populated: a node's `authorities/` is empty where an operator's is the point, and a node's `rete.json` carries a node name where an operator's carries none, an operator tree belonging to a rete rather than to a machine in it. `retectl` reads the trust domain out of that record like any other holder, never off the directory it found the tree in ([Enrollment § Decision Log](../enrollment#decision-log), ENRL-C0-40). The repository holds YAML source and the compiled tree and no secret and no certificate. The root key stays there in C0 — no command takes a path to it — and the hardening that would justify one is an intermediate; see [Enrollment § Genesis](../enrollment#genesis).
- **A command group is named for its subject, never its actor.** `id issue` produces an identity; a bare verb like `compile` or `publish` acts on the rete implicitly. There is no `ca` group in C0: `retectl init` is the only thing that creates a root CA, and a group for CA rotation arrives with rotation. Throughout these pages a **root CA** is an issuing authority and a **trust anchor** is what a verifier validates against; a bare "CA" is never used, because the two stop coinciding as soon as intermediates exist.
- `retectl issue-bundle` computes which principals live on a node (from `users.yaml` + `services.yaml`), issues each of their certs, and packages them with the trust anchors and the node's artifact set as the committed tree holds it. One bundle per node, not per principal — a node hosting five services would otherwise mean five deliveries and five bearer files. The bundle carries no coordinator URL and no expected coordinator identity: `agent.json`'s `sync` block already names the coordinator, and a projected value transcribed into a second place is a divergence waiting to happen.
- `--kind` selects the SPIFFE path namespace and the X.509 extension policy. All six kinds (`user`, `service`, `node`, `management-plane`, `control-plane`, `vertex`) remain part of the identity model; TLS-capable kinds get `keyUsage: digitalSignature, keyEncipherment` + `extKeyUsage: serverAuth, clientAuth`, signing-only kinds get `keyUsage: digitalSignature` only — see [ADR-0005](/docs/implementation/adr/0005-use-spiffe-identities). What C0 exposes on the CLI is narrower: `id issue` accepts the signing kinds, and TLS-principal certs are issued as part of `issue-bundle` rather than one at a time.
- **A CSR-consuming sign command belongs to Flow B and is not part of C0** ([Enrollment](../enrollment)). Nothing in C0 reaches it — `id issue` and `issue-bundle` each mint and sign inside one process — so `retectl id keygen` and `retectl id sign` are named here as the shape Flow B will take, and are not implemented surface.
- **`retectl` warns on the certificates it touches** — the mgmt signer's at every `compile`, the root CA's at every `issue-bundle` — when either enters the last 20% of its validity, or 14 days, whichever is longer. It is the only component whose warning reaches the person who can replace them ([Enrollment § Decision Log](../enrollment#decision-log), ENRL-C0-33).
- `retectl compile` writes artifacts to `.flor/compiled/<node>/mgmt/` inside the repo (`agent.json` and `flor.json` per node, flat; plus `coordinator.json` on the management node). Artifacts contain **no filesystem references** — identity is referenced by SPIFFE ID and materialized by each node's identity store (see [Agent § Artifact handling](../agent#artifact-handling)). No secrets in artifacts; committing them turns the git log into an auditable shipment history. Nodes don't pull from git; they fetch from the coordinator (see [Coordinator](../coordinator)).
- `retectl publish` uploads the current `.flor/compiled/` tree to the rete's coordinator; nodes fetch their own artifacts on the next `flor agent sync`. Publish is separate from compile so the operator can review the diff (and the audit commit) before the change is visible to nodes: publish is the review gate. Publish is idempotent — re-running with the same tree is a no-op on the server.
- **The operator's order is `compile` → review → commit → `publish` → `issue-bundle`, and only the commit is enforced.** `issue-bundle` refuses an uncommitted compiled tree and requires nothing else — not a successful publish, not a reachable coordinator ([Enrollment § Decision Log](../enrollment#decision-log), ENRL-C0-35). The repository is the rete's source of truth and the coordinator is a cache of it, so a bundle is cut from the source; publishing promptly is what keeps the cache from lagging, not a precondition of issuing. That independence is deliberate and load-bearing: a dead management node is repaired by re-enrolling it, which needs a bundle, so a bundle that needed a publish would need the coordinator it is meant to replace (ENRL-C0-37).
- **`retectl publish` is the only command that needs the network, and the only one that needs the local agent.** It reaches `coordinator-publisher` through the operator's SOCKS5 listener, discovered over `agent.sock`; everything else — `init`, `id issue`, `issue-bundle`, `validate`, `compile` — is fully offline. See [retectl local wiring](#retectl-local-wiring) below.
- Nothing in `retectl` affects running agents directly. It reads and writes the rete repo plus operator-local CA material, and talks to the coordinator over the rete's own Florete. Safe to run anywhere the operator has the repo checked out and is enrolled as an operator principal.

#### retectl local wiring

`retectl publish` talks to `coordinator-publisher` over the rete's own mTLS, so it needs a way into the rete. It reaches one through the local `flor` agent rather than through configuration of its own.

- **It is told one thing per rete: the operator's own principal name**, in `~/.retectl/retes/<scope>/config.toml` — written as a commented template by `retectl init`, and filled by hand. There is no prompt and no `--operator` flag, because `init` runs once per rete on one workstation while every other operator, and the same operator's second machine, arrives by `git clone` and never runs it; filling the value at `init` would serve only the machine that needed it least. A `publish` that finds the key unset fails naming the file, the key, and the principals in `users.yaml` carrying the `operator` role — the legal values, not just the schema. That fact is not derivable — the repository describes the rete, and what is missing is which human is at the keyboard; a rete may declare several operators, so "whichever principal holds the `operator` role" does not answer it either.
- **The address is derived, never configured.** `retectl` looks up the per-rete control socket (`agent.sock`, under the scope's runtime root — the same socket `flor agent status` uses) and queries the agent's endpoint-discovery map for that principal's local inbound. The agent answers `127.0.0.1:NNNN` from its compiler-projected `inbounds` map, staying role-agnostic — roles are compiled away, and the agent knows principals, not roles — and `retectl` uses that as its HTTP client's SOCKS5 proxy. A principal name is stable and a projected port is not, which is why the stable half is the configured half.
- **`--socks5 127.0.0.1:NNNN` is the escape**, and it is settable in the same file rather than only as a flag. It covers an agent that is not running, an operator who prefers not to depend on one, a user-mode `retectl` against a system-mode agent — and the case where `agent.sock` has not shipped at all, in which case configuring the address is the accepted degradation rather than a rejected option.
- **The publish target is derived, never configured and never named on the command line.** `coordinator`, `coordinator-publisher` and their groups are **reserved names** the validator enforces ([Coordinator](../coordinator)), so the destination is `coordinator-publisher` under the repo's `rete.name` — a rete-scoped principal, with no node segment, which is the same value the compiler projects into every node's `agent.json` sync block. `retectl` is that compiler, so publish reads a fact it has just computed rather than discovering one.

The coupling is shallow and deliberate: `retectl` needs the rete-scope `agent.sock` and the repository path, and nothing else of flor's.

The decisions behind this section — what `retectl` is told, what it derives, and why `agent.sock` is not a public interface — are recorded as **ENRL-C0-09** and **ENRL-C0-10** in [Enrollment § Decision Log](../enrollment#decision-log); this page collects the CLI of many features and keeps no log of its own.

### flor (node, daemon + user CLI)

```
flor enroll <bundle>                        # bootstrap a scope: take the scope lock,
                                            # verify, write the identity plane, deposit
                                            # the artifact set. Activates nothing —
                                            # prints the flor agent enable that does.
                                            # Refuses while the scope is live, naming
                                            # the holder and the flor agent disable
                                            # that clears it. No flags: every check is
                                            # mechanical and runs the same attended or
                                            # not. Needs no network. Prints the trust
                                            # domain and the anchors' fingerprints
                                            # before writing anything — a display, not
                                            # a check. Refuses a delivered cert that
                                            # does not chain to those anchors.
                                            # Deletes the bundle on success.
                                            # Re-enrolling validates the manifest's
                                            # signer cert against the anchors the node
                                            # already holds, then the signature, then
                                            # refuses any bundle differing from what
                                            # the scope is pinned to — trust domain,
                                            # anchors or node. The scope is the rete name
                                            # verbatim; a collision between two
                                            # independent retes of one name is a refusal
flor install [--system|--user]              # install or upgrade this host: place executables
                                            # + per-OS service wrappers, write the install
                                            # receipt; run by install.sh; idempotent.
                                            # Any release installs over any other — going
                                            # back is installing the older one — and it
                                            # never changes which scopes are active.
                                            # Migrations are not its business (see Installer)
flor uninstall [--purge]                    # stop agents, remove what it placed: binaries,
                                            # wrappers, runtime roots, receipt and lock.
                                            # Scope roots, config.toml and the flor user
                                            # survive unless --purge (see Installer)
flor version                                # release version, install mode, every resolved
                                            # directory, and the release this one replaced

flor agent run    [--rete <scope>]          # the supervisor daemon (run by the OS service
                                            # wrapper); reads agent.json from the active
                                            # artifact set; auto-detects the scope if only
                                            # one rete is enrolled; supervises one
                                            # `flor-vertex` in C0 (+ coordinator on mgmt01).
                                            # One agent per scope, enforced by a per-scope
                                            # lock in the runtime root
flor agent sync   [--rete <scope>]          # fetch + verify + install latest artifacts,
                  [--dry-run]               # then restart the vertex. Scope auto-detected
                                            # if only one rete enrolled. --dry-run shows
                                            # which version would install, no restart.
                                            # (commit-timeout/--confirm land in C1)
flor agent status [--rete <scope>]          # local agent state + active artifact version
flor agent enable  [--rete <scope>]         # activate this scope's service wrapper and
flor agent disable [--rete <scope>]         # start it; disable stops and deregisters it.
                                            # Scope auto-detected if only one rete is enrolled,
                                            # as elsewhere. Needed to resume a scope that
                                            # survived an uninstall, and to leave one rete
                                            # without touching others (see Installer)

```

### flor-vertex (agent-spawned, data plane)

```
flor-vertex       [--rete <scope>]          # the data-plane daemon. In production the agent
                  [--name <name>]           # spawns it with full FLORWL_* context — no flags.
                  [--set <version>]         # Flags exist for debugging only, as explicit
                                            # overrides of the same variables
```

### flor-coordinator (agent-spawned, management node)

```
flor-coordinator                            # the store-and-serve management-node service.
                                            # Spawned by the agent with the same uniform
                                            # FLORWL_* context and no flags of its own
```

Notes:

- **State directory.** Two deployment modes, chosen by the installer (see [Installer § Modes](../../installer#modes) and [Directories](../../installer#directories)): **user mode** (`$XDG_STATE_HOME/flor`, macOS included — personal devices, user-level service, and the only macOS mode in C0) and **system mode** (`/var/lib/flor`; servers, dedicated `flor` service user). Node-local commands resolve it as: explicit `FLOR_STATE_HOME` (one of the per-directory development/CI overrides), else the column of the [directory table](../../installer#directories) selected by the mode the invoked binary infers from its own prefix — so which install a command acts on is which binary you typed, and `flor version` prints the answer. The directory holds `retes/<scope>/` per enrolled rete, created by `flor enroll`, plus two files belonging to `flor install` alone — its receipt and its lock, which no other install channel writes. Enrolled retes live at `<state-dir>/retes/<scope>/`; config, sockets, and executables have directories of their own.
- **Flow B has no command in C0.** The security-purist path — a principal generating its own keypair and sending only a CSR — is deferred (an open question for C1, see [C1 Scope](/docs/implementation/c1-manual-mesh/scope)), and its commands are `retectl id keygen` and `retectl id sign` when it lands: identity work is `retectl`'s, and a principal running `retectl` on its own machine is running a tool the installer already put there.
- **`flor enroll <bundle>` takes the scope before it reads the bundle.** It creates `retes/` and the scope root if either is absent, takes the **scope lock**, and refuses when someone already holds it — naming the holder, and the `flor agent disable` that clears the ordinary one; it never stops a running agent itself ([Enrollment](../enrollment#decision-log), ENRL-C0-39). Under that lock it reads `receipt.json`, gating the scope root's `schema_version` and taking the phase as its answer to fresh-or-re-enrollment. Only then does it verify the bundle: on a re-enrollment, the manifest's signer certificate against the anchors the node already holds, its `management-plane` kind, and then the signature; always, every entry against the manifest's digests, and every certificate it is about to write against the anchor set it is about to pin, refusing one that does not chain; then it prints the trust domain and the anchors' fingerprints, as a display rather than a check — there is no flag turning it into one. **The first enrollment pins the trust domain, the anchor set and the node**, and a later bundle differing in any of the three is refused rather than applied, so re-enrollment reaches principal material and the artifact set alone (ENRL-C0-13). It then writes `receipt.json` with phase `enrolling`, writes the identity plane — `identity/anchors.pem`, `identity/rete.json` recording the trust domain and the node from the manifest's claims, and `identity/principals/` — replacing the material of each principal the bundle names and leaving every other principal's alone, and **deposits** the bundle's artifact files in `incoming/`, which carries no set structure and no pointer — staging is a step inside the agent's intake, and enroll performs none of it. It finishes by replacing the receipt with phase `enrolled` — the **commit point**, before which the scope counts as not enrolled — deleting the bundle, printing the `flor agent enable` for this scope, and exiting, which releases the lock. **`flor agent enable` is what activates**, and the same command resumes a scope that survived an uninstall with no bundle at all. The agent then takes the scope lock, refuses a receipt that is absent, mid-run or unreadable, and otherwise admits `incoming/` **before its first dial** and syncs; enroll's success means the material is written and the files deposited, not that the set is running, so a rejected intake is logged at WARN once. A run interrupted anywhere **converges**: any bundle this scope would accept completes it. None of this needs the network. The scope is the rete's name verbatim; two independent retes of one name cannot both be enrolled on a host, and that is a refusal. The bundle is deleted on success.
- `flor agent sync` is a **thin client of the running agent's socket** — the daemon executes the sync (it also syncs once at startup and on a poll timer — interval set by `poll_interval` in `agent.json`'s `sync` block). The daemon polls the coordinator with the held set version (a no-op while unchanged — the cheap poll), fetches and verifies the complete new set when it moved (acting as the `node/<node>` principal via the local vertex's SOCKS5), stages it, activates it via the `mgmt/current` pointer, and restarts the workloads whose payloads changed — restarting itself through the service wrapper when its own payload changed. Fetch → verify → stage → restart; see [Agent § Sync](../agent#sync). No compilation on the node — artifacts were pre-compiled by the operator and published to the coordinator.
- **No commit-timeout / auto-rollback in C0.** A sync activates the new artifacts and restarts the vertex; there is no confirm-or-roll-back guard. The Cisco-IOS-style `commit confirmed` safety net lands in [C1](/docs/implementation/c1-manual-mesh/scope). In C0 a bad sync is bounded by keeping an out-of-band emergency-access path (see [Distribution & Reload · Safety Net](../distribution-and-reload#safety-net-server-nodes)), which suffices for limited pilots that never rely on Florete as the single access path.
- `flor agent run` is the long-running supervisor process per node. It reads `agent.json` from the active artifact set and forks a child per entry in its `workloads` inventory, in list order — each entry's `run` argv spawned with the uniform `FLORWL_*` environment (see [Agent § Supervision contract](../agent#supervision-contract)). In C0 that's one child (plus the coordinator on the management node); C1 adds a second vertex for the mesh-flor layer. Launch mechanics are pinned in [Agent § Supervision mechanics](../agent#supervision-mechanics): the OS service manager keeps the agent alive; the agent forks and supervises its workloads directly (restart backoff, exit-code vocabulary, liveness window); per-workload launch runtimes (system units, containers, remote WRI) are a reserved evolution.
- `flor-vertex` is the data-plane daemon. In production the agent spawns it with the uniform `FLORWL_*` environment (see [Agent § Supervision contract](../agent#supervision-contract)): it reads the config `FLORWL_MGMT_ARTIFACT` points at (plus `FLORWL_CTRL_ARTIFACT` for a mesh vertex), resolves identity material against the scope root, and runs the workloads/io/transport-endpoint/connection-manager described there. The CLI flags are **debug-only overrides of the same variables**, all explicit: no auto-detection, and the vertex never reads the `mgmt/current` pointer — one uniform resolution path whatever the source. It does **not** re-verify signatures (the agent is the sole verifier); it is unaware of the agent, the coordinator, and the rest of the rete.
- `flor agent status` reads from a **per-rete Unix socket** (`agent.sock`, under the scope's runtime root — `/run/flor/<scope>/` or the user-mode equivalent) exposed by that rete's agent. The socket speaks a structured protocol; `status` renders it for humans, and tools read fields directly — `retectl` uses the endpoint-discovery map this way. `--rete <scope>` selects which socket to use; auto-detected when only one rete is enrolled. A future tray-icon GUI (B1+) will be another client of the same socket — CLI and GUI share the same daemon API.

**Explicitly deferred from C0**:

- Any YAML-mutation subcommands.
- Flow B / CSR-based enrollment wired into onboarding (`retectl id keygen`, `retectl id sign`) — open question for C1.
- Multi-hop paths and label allocation (C1 feature).
- SIGHUP hot reload.
- CRL / OCSP. (Revocation is by name removal + `flor agent sync`.)
- Delta state updates.
- iptables-based transparent outbound redirection for services that can't speak SOCKS5.
