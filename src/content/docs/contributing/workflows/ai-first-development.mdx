Florete is built by two implementation lines working from one design corpus. The spec-driven line is generated by agents, released and maintained. The decision-driven line is human-designed and grows behind it, one unit at a time. Neither replaces the other: we release first and build afterwards, and the frontier between them never closes.

If you are proposing a change, [Working on Florete](#working-on-florete) says where it goes and what it has to carry — that is all most contributors need. The Shape and the sections after it explain the process itself, for whoever changes it, and the Decision Log at the end records why each rule is what it is.

## Working on Florete

Contributions go to two repositories: design and documentation to [`florete`](https://github.com/rete-labs/florete), which holds the corpus this page is part of, and code to [`flor`](https://github.com/rete-labs/flor), the decision-driven repository. [`flor-dist`](https://github.com/rete-labs/flor-dist) is public so that anyone running Florete can inspect what they run, but it takes no patches: its code is generated, and a unit is replaced wholesale whenever it is regenerated, so a hand-written change there would be thrown away rather than kept. Report a defect you hit in a release as a failing test against `flor` instead. That test outlives every implementation of the unit it covers, which a patch would not.

Use AI throughout — that is what this page is about — and understand what you propose. Every change to `flor` is reviewed by a human and has to be defensible line by line: what typed it is not the question, whether you can answer for it is. Fully automated work is not accepted there, and that is what the other line exists for; keeping the two apart is the point of the whole arrangement.

Start a feature at [Design](../design) rather than at the code. That page carries the design workflow we run — decisions settled and recorded before any prose is written — and it is what decision-driven development means in practice on the DD line: the decisions exist, in writing, before an implementation does. Both lines consume the whole corpus; what differs is what each requires of it — SD can be generated from scope and contracts alone, and consumes the decisions if they are available, while DD cannot proceed until they are settled. An implementation counterpart to that workflow will join it. Behaviour therefore starts in the design corpus — the milestone pages under `implementation/`, and the guides, which are input to the lines rather than a deliverable that follows them — not in a pull request, since those pages are the specification both lines are built from and behaviour that lands only in code leaves the two lines describing different products.

A bugfix carries a failing test first: write it into the conformance suite, watch it fail, then fix. This is not ceremony. The suite is never regenerated, so that test is what makes your fix survive the next regeneration of the code it fixed.

## Process design

### Why two lines

Agents and humans fail at different things, and the split follows that. Agents are good at producing a working implementation from a specification and poor at carrying one through a sequence of changes — structure erodes as the sequence lengthens, and better prompting moves where the erosion starts without changing how fast it accumulates. Humans are the opposite: slow to produce, and the only thing that holds a system's shape across time.

So the spec-driven line takes the work agents do well, and the decision-driven line takes the work humans do well while accepting that it cannot move fast enough to be the product on its own. Running only DD settles quickly: there is no sellable artifact inside any funding window we have. Running only SD is the harder case, because it would work for longer than it looks. The contracts are what make a system evolvable, not the code behind them, so a generated product with good boundaries can be extended by regenerating a unit inside the boundary that holds it.

What such a product would lack is evidence. A green suite would be the only thing saying it is right, so every requirement would have to be cheaply testable from outside, and every test added would constrain every later regeneration — the erosion would move out of the code and into the suite rather than going away. Nobody could diagnose a live defect in code no one has read. No implementation experience would feed back into the corpus, which is the asset the rest of this rests on. And a contribution would have nowhere to land, since the generated repository takes no patches. DD exists for those four things, and evolvability is not among them.

The same reasoning splits the human loop by property rather than by volume. Humans own scope, acceptance, the failure modes, the security boundary, the suite, the runbook and every unit's public API on both lines; on DD they also own structure, naming, implementation detail and the review of every diff; on SD they own none of those, and no generated code is reviewed at all. That is affordable because the properties agents fail at do not fail together — happy-path correctness is good, the evolvability of what an agent writes is given up deliberately, failure-path and security correctness are weak — and it is bounded by one failure with no other check behind it: what an edit drops. An agent can delete the line that verifies something and leave every test passing, and on a line nobody reads that goes unnoticed. Reading the diff is the only check against an omission, which is what the DD units are buying.

The frontier never closes, and that is the design rather than a failure to finish. New work lands SD-first because that is where speed is, and a unit moves DD-ward when something says it should rather than on any schedule — what says so, and what the move costs, is settled under Substitution below.

### The corpus

One rule keeps the arrangement from collapsing. The corpus flows to both lines and DD crates flow to SD, but nothing flows out of SD except findings: what the generated line learns about the design is filed against the corpus and enters through a design pass, never as a direct amendment made under release pressure.

That rule is also what defines the corpus. It is everything SD generates from — and since nothing flows out of the generated line, whatever that line generates from is by construction ours to author. "What must a human own" is therefore a consequence rather than a judgement made case by case.

It has two homes. The prose half is in `florete`: a milestone's scope, its decisions, and the operator and user guides, which bind as input rather than following the code and which carry the use cases that have to work. The other half is the contracts, and they live as code in `flor`, because a public API in Rust is not prose and belongs where it compiles. Both lines consume all of it, and what differs is what each requires: SD can be generated from scope and contracts alone and takes the decisions where they exist, while DD cannot start until they are settled.

A DD implementation is not corpus at all. `flor-dist` depends on DD crates, and building it puts their bodies within the agent's reach, but generation codes against their interfaces and never against their bodies. An agent that relies on a body codes against what it observes instead of what was promised, and the invariants it absorbs that way become load-bearing without anyone having written them down, which surfaces as a silent break the next time DD refactors behind its contract. It does that where a contract is silent, so the rule is to report rather than to look away: behaviour generated code relies on that the contract does not state is filed as a finding, which is how a contract learns it had a gap. One convenience falls out of coding against contracts: a contract can be tagged before its body exists, so a crate whose functions are unimplemented still yields a complete interface, and SD generates against a frozen API while DD fills it in. Only the assembly move waits for a working implementation.

Because a contract is corpus, changing one is a design decision. An agent that finds a unit's API wrong, or missing something it needs, proposes the change as a finding and a human takes it through the pass — that is among the more useful things generation reports, and it is still not a licence to write one.

### Units and contracts

Before a milestone is generated at all, one class of thing has to be designed: whatever a regeneration cannot undo. That is anything read from outside the unit — another component reading a public API, a later version reading on-disk state or an artifact format, a peer reading a wire format, a person reading the CLI or an error message. Everything else is the agent's to decide, because being wrong about it costs one unit's regeneration rather than a break in something already deployed.

A unit is a crate whose public API a human writes before either line implements it. Being contracted is what makes it a unit, so there is no such thing as an uncontracted one — only code that is not a unit, bound by the corpus and the suite and by nothing else. SD and DD each supply a crate satisfying that API, and a substitution is a one-line change, in `flor-dist`'s workspace root, to which of them supplies it. A binary's own logic can be a unit like any other — what a unit names is a contract, and which line satisfies it is decided where the graph is assembled rather than by where the code sits; the executable is then built in `flor-dist` from a one-line `main` over that unit's entry point. Which code is a unit, and which is not, is recorded per milestone in `decomposition.mdx`.

The boundary is a crate rather than a module because a module boundary inside one crate is advisory: `pub(crate)` is visible throughout, so in a codebase nobody reads it erodes without anyone noticing. A crate boundary is checked by the compiler, and conformance is checked the same way wherever the contract's form allows — by a tool rather than by a reviewer. A human reviews the API; a public-API diff enforces it, and fixtures enforce the external contracts beside it in the same gate.

Not everything becomes a unit, because authoring an API costs human time and that is the scarce resource. The first rule is fan-out: code read by every binary is drawn as a unit before generation, since retrofitting a boundary there later means regenerating most of the line, while code with one caller waits until extracting it is worth a regeneration of its own area.

The second rule is not about cost at all, and either rule alone is enough. Some code is drawn as a unit, and authored on DD from the start, because of what being wrong there would mean. Two questions decide it. Does its obligation quantify over all inputs — no peer without a valid SVID accepted, no path emitting key material, no traffic crossing between retes? A suite is evidence about the inputs it uses, so a promise of that shape is beyond it: the input that matters is chosen by an adversary after we chose our tests. And can being wrong be taken back? Where a defect costs what the next release cannot undo, or disables the path by which everything else is repaired, the model's trade of a mistake against one regeneration is not the trade being made. The transport endpoint answers yes to both, which is why it is the example: mTLS terminates there.

Some contracts are not interfaces at all. Error handling is the case in point: a type constrains nothing by itself, since a unit can satisfy every signature and still discard context at each boundary. What is contracted there is a style — how errors are wrapped, what context is attached, and that the resulting stack stays readable to an operator during an incident.

A contract therefore takes the form its subject needs, and an API is only the most obvious one. A data format is contracted by fixtures. A user-facing surface can be contracted by the guide that documents it: the guide is written before either line implements anything, the agent can generate the main-line tests from it, and what a formal suite would add there is mostly transcription. A style is contracted by rules plus golden output. Behaviour is contracted by conformance tests, but only where nothing cheaper pins it. Detail is graded the same way — a surface whose misuse costs a support question is described, where one whose misuse costs a breach is specified — and enforcement follows the form: mechanical where the form allows, by review on DD where it does not, and by nothing on SD where neither reaches, which is a cost of the arrangement rather than an oversight in it. These forms are what we expect to use rather than a settled set; authoring A0's contracts for real is what will decide which of them survive.

Two failure modes sit either side of this. Contracting too little leaves the agent to freeze something a later version has to read. Contracting too much spends the scarce resource on transcription and, where the over-contracting takes the form of tests, buys a suite that eventually blocks the regenerations it exists to make safe, since every test is a constraint the next implementation has to satisfy.

APIs are not authored cold. The agent proposes one and generates consumers against it, and a human judges the result and iterates. Consumers are what reveal a bad API, and generating throwaway consumers is the cheap operation here. The work belongs at the very beginning: while DD has no call sites and SD is small, changing an API costs almost nothing, and it grows more expensive on both sides from then on.

This is where the arrangement is most exposed, and it is worth saying plainly. Nearly all of the risk has been moved into the one activity with no mechanical check behind it: a public-API diff enforces conformance to a contract and says nothing about whether the contract was any good. So the failure this process invites is not a mess. It is a clean, conforming, well-tested system built on the wrong boundaries — which stays invisible far longer than bad code would, and costs far more once it surfaces. The one signal available is late: a unit that resists substitution, or whose contract keeps moving, is reporting that its boundary was drawn in the wrong place.

### Change, regeneration and the suite

On DD the unit of change is the diff. On SD it is the unit: affected units are regenerated from the corpus rather than edited toward a new shape, because editing is the operation that accumulates erosion. From the corpus, not from a fixed list of pages — the agent gathers what it needs, milestone and neighbours included, and no map says which pages a unit answers to. A regeneration is not expected to arrive at the previous implementation either. Fresh context, and in a year a newer model, are what make it come back different, and that is the point of regenerating rather than patching.

Patching is allowed behind a failing conformance test, and that test is the whole admission rule. Admissibility has to be decidable without reading the code: a failing test is, and a judgement about how large a change is would not be, since making it would need the review this line does without.

Patching stops at a ceiling. When fixes reliably produce new defects, when a contract moves in a way the implementation behind it cannot absorb, or when a milestone's requirements diverge far enough that adapting costs more than generating, the unit is regenerated instead.

None of that is survivable without the suite. It is append-only and never regenerated, so every defect ever captured is inherited by every future implementation of the unit — a regenerated unit comes back with different bugs rather than the same ones, and the suite is the entire difference between that being acceptable and not. It holds conformance tests written against contracts, saying what the product promises, and regression tests, one per defect, saying what it once got wrong. What it must carry is what nobody would reconstruct: the promises the product makes, and the failures it has already met where they still matter.

The agent does not read it while generating. It works from the corpus, and the suite judges what came out; a test becomes input only once it fails, which is the patching rule again. What stays visible throughout is a defect ledger — one line per defect captured, no assertions and no fixtures — so a fresh implementation can avoid the traps already met without being written against the oracle. Generated against the suite it would converge on the implementations whose defects filled it, which is the opposite of coming back different, and where the suite is silent it would fill the gap arbitrarily while a wrong test would simply become the specification.

Kept as a gate, a failure carries information instead: either the agent misread the corpus, or the corpus and the suite disagree — and the second is a finding. That works because a conformance test's obligation belongs in the corpus in any case, the test being the executable form of a promise rather than a new requirement, so a test that cannot be derived from the corpus is a gap in the corpus and not a rule withheld from the line that has to satisfy it. Whether the patching this costs is cheaper than the convergence it avoids is the honest open question here, and A0 is where the two get compared.

### Substitution

A unit moves DD-ward when something says it should: the threat-model pass flags it, or its defect rate crosses the ceiling. Never a quota — the need is observable, and allocating the work by arithmetic invites gaming it. Among candidates, severity decides and shape breaks ties, since a data-shaped unit drops into any consumer while a lifecycle-shaped one brings a runtime and a shutdown protocol with it. A unit can move once everything it depends on is contracted, which is a much weaker condition than everything it depends on being DD-authored.

The step itself is fixed. Freeze the unit's contract; have `flor-dist` build a second configuration that takes the DD crate by git tag where the first takes the SD one by path; require the suite green in both; land the assembly move; then delete the SD implementation. The suite is black-box over the product, so a DD crate is never green on its own — only a build of the product carrying it is, which is why the second configuration exists before the move rather than after it. Deleting last is what keeps every earlier step reversible by the same one-line change, and running both configurations is what catches a DD crate that passes on its own terms while changing behaviour the product depends on.

Both configurations are expressed in one place. `flor-dist`'s workspace root names a source for every dependency it declares itself, and redirects, through a `[patch]` entry over the `flor` source, the ones declared inside DD crates — which is what lets a DD unit sit above generated ones instead of dragging reviewed implementations down the whole subtree beneath it. The constraint that comes with it is that each unit must resolve to exactly one package in the graph: Cargo will otherwise resolve two revisions of one unit without complaint, and unless a type happens to cross between the copies, the product ships both of them and both of whatever state they hold. Enforcing that mechanically is what keeps a unit's pin its own rather than the repository's.

DD work happens in the gap after a release rather than alongside the next one. Scheduled in the same window the two compete for the same people, and SD wins every time — it has customers where DD has principles.

Each release reports the share of units that are DD-authored, which ones moved since the last, and how much of the security-relevant surface the share covers. The failure mode of this arrangement is not that the migration never finishes — it is not meant to — but that the frontier stops advancing because new work always outranks moving a unit. A bare ratio would not show that on its own, since we define the units it counts and a re-decomposition moves it without moving anything; naming the units that moved is what makes the frontier visible without dictating a response.

### Releases and assurance

Milestones do two jobs. They decompose the design, which is why A0 and C0 exist at all — designing C1 whole proved intractable — and they are release points. SD generation starts at A0 scope and grows a milestone at a time.

A0 is 1.0.0 and semver applies verbatim from there. A milestone usually breaks compatibility and so usually takes a major; one that did not break would not bump it. A candidate is built, passes CI, and goes to the test environment as `X.Y.Z-rc.N`; approval promotes it to `X.Y.Z`, which is a rebuild at the release version rather than a re-tagging. A release candidate is not a release, and carries no release note.

Every release carries a note naming who it is for, what it does and does not do, and what is promised. Early milestones are testbed and dogfooding artifacts and say so plainly, because "release" implies usability and support and a milestone that sells nothing must not borrow that. Everyone gets a supported-version window and security advisories; paying customers add a response time and a fix turnaround. Availability is never promised — through the C line the software runs on the customer's own hardware and network, which we neither control nor can measure.

Each milestone is security-audited over the product it releases, DD-authored units included. The pass is a human threat model over that whole surface, plus an AI-assisted code audit of it, run by a different agent than the one that generated it, since a generator and an auditor sharing a model share blind spots. An independent audit precedes the first customer milestone, and where it cannot be funded the release states that limitation rather than shipping quietly. We do not audit our own foundations: knowing the invariants a design intended is precisely what an auditor must not assume, which is a matter of context rather than skill.

What we say publicly about all this is the model and its current state, including the DD-authored share — not that AI was involved. "Parts of this are AI-generated" is a sentence any slop project also writes, so as a disclosure it carries nothing. The claim worth making is that the boundaries are human-owned and the units are being replaced by reviewed implementations, which is a claim a vibe-coded product cannot make.

## Decision Log

Entries are grouped by what a future change would be touching, not by the order they were settled.

### The model

**AIFIRST-01. Run two permanent implementation lines over one design corpus.**
The spec-driven line (SD) is agent-generated, released and maintained. The decision-driven line (DD) is human-designed and grows behind it by substitution. Both are built from the same design pages, and neither converges away.
*Because* DD alone cannot reach a sellable product inside any relevant funding window.
*Because* what SD alone lacks is evidence rather than evolvability: the contracts are what make the system evolvable, and a unit is regenerated inside its boundary when requirements change, but then the suite is the only thing saying the product is right, nobody can diagnose a live defect in code no one has read, no implementation experience feeds back into the corpus that both lines depend on, and a contribution has nowhere to land.
*Accepting* permanent maintenance of two lines, and that some units stay SD-authored indefinitely.
*Rejected* running SD alone behind good contracts and a good suite — it is structurally evolvable, but it makes the suite the system's whole memory: every requirement has to be cheaply testable from outside, and each test added constrains every later regeneration, so the erosion moves from the code into the suite rather than going away.
*Rejected* replacing SD wholesale once DD reaches parity — parity is not a state that arrives, since features keep being added ahead of it, and DD is needed only where the suite is not sufficient evidence. Rebuilding the rest by hand would buy nothing.

**AIFIRST-02. Treat milestones as design-decomposition units and as release points.**
A0, C0 and C1 exist because designing C1 whole proved intractable, and that remains their purpose. Each is also a release, and further milestones may be added to divide the work more finely.
*Because* the dual process exists to release more often, and a milestone that cannot be released makes releasing harder.
*Accepting* more scope pages; the design content does not grow, only its division.
*Rejected* letting milestones drive version numbers — releases are more frequent than milestones.

**AIFIRST-03. Start SD generation at A0 scope.**
*Because* the whole machine — contract authoring, generation, substitution, regeneration — is unproven, and A0 is the cheapest place to be wrong about it. Starting early is what refines the process.
*Because* releasing early and often is what buys reality checks, and the earliest ones come from ourselves and from early adopters long before they come from customers.
*Because* A0 needs neither of the unregenerable designs C1 requires, so generation begins while those are still being authored.
*Accepting* that the sellable artifact arrives later, and that A0 rehearses only the data-shaped substitutions.

**AIFIRST-26. Define the corpus as everything SD generates from.**
It has two homes and one test of membership. Prose lives in `florete` — a milestone's scope, its decisions, and the operator and user guides, which bind as input rather than following the code. Contracts live in `flor`, as the public API of every unit, because a Rust API is not prose and belongs where it compiles. A DD implementation is not corpus: SD depends on DD crates, but generation codes against their interfaces only (AIFIRST-27).
*Because* nothing flows out of SD, so whatever SD generates from is by construction ours to author — which makes "what must a human own" a consequence of the direction rule rather than a judgement made case by case.
*Because* the guides define the use cases that must work, which is a stronger input than the design pages and the reason they are written before either line implements anything.
*Accepting* that the corpus spans two repositories.

### What gets contracted

**AIFIRST-04. Design before generation only what a regeneration cannot undo.**
A contract is authored first when something outside the unit reads it: **another component** (a unit's public API), **a later version** (on-disk state, artifact formats, configuration schema), **a peer** (wire formats), or **a person** (the CLI, error output and the guides — the user-facing surface). What lives inside a unit is the agent's to decide.
*Because* a decision SD makes that later constrains DD is one taken without gates and cannot be regenerated away, while everything else costs a single unit's regeneration.
*Revisit* what a deployment counts: metric names and their meanings are not contracted yet, and become user-facing surface the moment monitoring is added.
*Rejected* closing each milestone's design fully first — most of what remains is regenerable detail. *Rejected* letting the agent decide every gap — it would freeze a wire protocol and a user-facing surface with no review.

**AIFIRST-05. Decompose the product into units, and check every contract the strongest way its form allows.**
A page `implementation/<milestone>/decomposition.mdx` holds the decomposition and grows with the milestone. A unit is a crate whose public API is authored before either implementation (code with no contract is not a unit, bound by the corpus and the suite and by nothing else). SD and DD each supply a crate satisfying the API, and substitution swaps which one the assembly selects. Conformance is checked by tools in `flor-dist`'s CI — internal contracts by public-API diff, external ones by fixtures — in one gate. A contract's form follows its subject, an API being only the most obvious: a format is fixtures, a user-facing surface can be the guide that documents it, a style is rules plus golden output, and behaviour is conformance tests where nothing cheaper pins it. Detail follows consequence, and enforcement follows form — mechanical in that gate where the form allows, by review on DD where it does not, by nothing on SD where neither reaches. A human reviews the contract; nobody reviews the implementation.
*Because* the corpus specifies behaviour but never drew code boundaries, and a boundary retrofitted into generated code is an evolution step on that code.
*Because* a crate boundary is compiler-enforced where a module boundary is advisory, and in code nobody reads, an unenforced boundary erodes unnoticed.
*Because* the suite captures bugs that were found rather than everything that was promised, so it cannot be the only gate.
*Accepting* coarse granularity — a few large crates with real APIs.
*Accepting* that a suite grown past what it must carry becomes the constraint a fresh implementation cannot satisfy, so over-contracting behaviour costs the regenerability the model runs on.
*Revisit* the set of contract forms and what enforces each: the list above is what we expect to use, and authoring A0's contracts for real is what will settle it.
*Accepting* that this concentrates the risk where nothing checks it: the diff enforces conformance to a contract, never the fitness of one, so a wrong boundary produces a clean and well-tested system that is expensive to correct and slow to notice. The available signal is late — a unit that resists substitution, or whose contract will not settle, is reporting a boundary drawn in the wrong place.
*Rejected* deriving the boundaries from whatever structure SD arrives at.

**AIFIRST-06. Draw high-fan-out boundaries as units before generation.**
Code read by every binary becomes a unit first. Low-fan-out code — the compiler, a per-command layer, an inbound or outbound adapter — stays outside the inventory until extraction is worth a regeneration. What is a unit and what is not is recorded per milestone in `decomposition.mdx`.
*Because* the cost of adding a boundary later is proportional to its call sites, and that is knowable from the corpus in advance.
*Accepting* that code left outside the inventory and later found to need DD work costs a regeneration of its area.
*Rejected* making everything a unit — authoring every API without practice is the failure this avoids. *Rejected* making none — code that isn't a unit is exactly what cannot be substituted cheaply.

**AIFIRST-07. Draw a unit where a suite cannot be the evidence, or where being wrong cannot be taken back.**
Two questions decide it, and either answer alone is enough, whatever the call-site count. **Does the obligation quantify over all inputs?** A suite shows that the inputs it uses produce the promised result. Where the promise is that *no* input produces some result — no peer without a valid SVID is accepted, no path emits private key material, no traffic crosses between retes — the input that matters is chosen by an adversary after we chose our tests, so a green suite says nothing about the gap and only reading the code does. The domains are not comparable either: we define what valid means, so a suite can cover the shape of that space and property tests can extend it, while its complement would need the adversary modelled to be generated at all. **Can being wrong be taken back?** The model trades on a defect costing one unit's regeneration. Where it instead costs what the next release cannot undo — a breach that has already happened, state destroyed on a user's disk, a node left unreachable — or where it disables the path by which everything else is repaired, that is no longer the trade being made, and review is bought as insurance. The transport endpoint answers yes twice, which is why it is the example: mTLS terminates there.
*Because* a test is evidence about the input it uses, so any universal claim is beyond a suite whichever way it points. What singles out the negative one is discovery: a universal positive fails toward the user, who notices and reports, and the field generates inputs at a scale no suite matches; a universal negative fails toward an adversary, who is the only party that learns. Field discovery is what stands in for proof everywhere else in this model — the suite, its users and the ledger between them — and this is the class where it is blind, so the check an agent drops is caught by the test that thought of it and by nothing else afterwards (AIFIRST-15). The universal positive that lacks field discovery too — every valid rollback succeeds, learnt during an incident — falls to the second question rather than this one.
*Because* AIFIRST-04's economics assume that being wrong costs a regeneration. Where the cost lands on someone else and cannot be reversed, the cheapness of regenerating is not the question being asked.
*Accepting* that such a unit may be lifecycle-shaped, and so the harder contract to author this early.
*Accepting* that the second question has no bright line — how far a consequence reaches is judged per unit, and the judgement is recorded beside it in `decomposition.mdx`.
*Rejected* "the defect would be silent" as the criterion — a specific silent failure is exactly what a conformance test catches, since one can feed the input that must be refused and watch the result, so visibility separates nothing. What defeats a suite is the quantifier, not the noise a failure makes.
*Rejected* an existing well-specified API as a reason to contract — several low-fan-out units have one, and having one says nothing about whether the boundary needs to exist before generation.

**AIFIRST-08. Govern error handling by a style contract, not by an interface.**
An error type appears in unit APIs like any other, but what makes error handling work is a set of rules: how errors are wrapped, what context is attached at each boundary, and that the resulting stack stays traceable across modules. The API side is enforced in CI with every other contract; the implementation side is enforced by golden error-output fixtures, and on DD by review.
*Because* a type alone constrains nothing — a unit can satisfy every signature and still discard context at every boundary, and a public-API diff sees none of it.
*Because* the error stack is what an operator reads during an incident, which makes it user-facing surface under AIFIRST-04 even though no signature expresses it.
*Accepting* that the implementation side is only partly enforceable: golden outputs catch what they cover, and on SD nothing catches the rest.

**AIFIRST-09. Arrive at a unit's API by generating consumers and judging the result.**
The agent proposes an API and generates consumers against it; the human judges and iterates. Logging and metrics need no interface of ours — the event stream is `tracing` and the counter mechanism is OpenMetrics — though what is counted is a separate surface, not yet contracted.
*Because* consumers are what reveal a bad API, and generating throwaway consumers is cheap. This recreates the practice loop that normally makes APIs good.
*Because* API churn is cheapest at the start, while DD has no call sites and SD is small, and grows more expensive on both sides afterwards. Front-load it.
*Rejected* authoring APIs cold. *Rejected* extracting them from a generated implementation, which lets its accidents harden into the contract.

### Repositories and code flow

**AIFIRST-10. Keep the lines in two repositories, `flor` and `flor-dist`.**
`flor` is the DD workspace, and it holds a crate for every unit, since a contract exists as compilable code before a body fills it (AIFIRST-27). `flor-dist` holds the SD implementations and the integration, assembles the graph, and packages every executable. They share no history. Binaries live in `flor-dist` because they are integration, not because a unit may not be one: where a binary's own logic has to be reviewed it becomes a unit like any other, with its crate in `flor`. Cargo builds a workspace's own bin targets and not a dependency's, so the executable is produced in `flor-dist` by a one-line `main` over that unit's entry point — assembly rather than implementation, and human-owned like the manifest around it.
*Because* the review regimes are incompatible: DD requires review of every diff and SD forbids it, so one repository would mean one CI, one CODEOWNERS and one set of protections covering opposite rules, with misclassification silent.
*Because* SD's history is regeneration-shaped, and wholesale rewrites in the same log would degrade blame and bisect for the line that depends on them.
*Accepting* that a DD binary can only be compile-tested in `flor`, against whatever bodies exist there; its real exercise is the suite, which only `flor-dist` can run.
*Rejected* branches or directories in one repository — a boundary held by discipline breaks on one inattentive command. *Rejected* naming the SD repository for the product — it is read mainly by agents and is not a front door.
*Rejected* forbidding a binary-shaped unit — a DD binary needs no dependency running from `flor` into `flor-dist`, because what a unit names is a contract and which line satisfies it is decided by the assembly (AIFIRST-11). Nor is the shim a consolation prize: the shape it makes possible is a unit sitting *above* generated units rather than only beneath them, which is what the assembly rule buys and what lets a binary's logic be reviewed at all. What differs from a library unit is enforcement — its contract is the CLI and the output, carried by fixtures and by the guide rather than by a public-API diff.

**AIFIRST-11. Move DD code to SD as git-tagged crates, and publish nothing.**
Each unit is its own crate, tagged on demand: when it becomes substitutable, or when a fix must reach SD. `flor-dist`'s workspace root is the single place that says which line supplies each unit — a dependency it declares itself by source, a path for an SD implementation and a git tag for a DD one; a dependency declared inside a DD crate by a `[patch]` entry over the `flor` source, which reaches transitively and unifies the graph. Substitution is a one-line edit there either way, and the patch table is a standing inventory of which units are still generated. Nothing goes to crates.io.
*Because* a copy would make every fix a two-site change, and duplication in the security core is the worst case of it.
*Because* publishing internal APIs creates an accidental SDK the real one would have to disambiguate — and nothing we would put on a registry has a user, since the installer ships binaries and `cargo install flor` was already retracted.
*Because* the graph will otherwise carry a unit twice and say nothing about it: Cargo resolves two revisions of one unit without complaint, and the compiler objects only where a type crosses between the copies — otherwise the product ships two of the unit and of whatever state it holds. So the assembly carries an invariant of its own: **each unit resolves to exactly one package in every build configuration**, enforced mechanically, and scoped to our own units so that ordinary third-party duplicates cannot mute it.
*Because* that check is also what keeps pins per unit rather than repository-wide: units that depend on one another are forced to a common revision by it, and units that do not are left independent — which is the constraint the dependency graph actually imposes, rather than a coarser one declared over the whole repository and paid for by dragging every unit's unreleased work along with each bump.
*Accepting* that `flor` and `florete` may be taken by someone else; the binary name, the crate names and the brand do not depend on the registry.
*Accepting* a third mechanical check in the gate, and that a duplicate unit is diagnosed rather than prevented.
*Revisit* when a third-party SDK is designed.
*Rejected* vendoring a copy.

**AIFIRST-12. Seed DD from the existing code; generate SD from the corpus.**
The current `flor` code is AI-generated under human review, so it is DD by nature: hardened to A0 and split into contract-satisfying crates, it becomes DD's first units. Its APIs open the loop in AIFIRST-09 and its CLI surface is reused. SD is generated from the corpus and inherits none of it.
*Because* seeding SD would make its first act an evolution step over pre-A0 code that does not match the design — the operation the model concedes agents cannot do — and would give SD an agent-mutated descendant of DD's own history.

**AIFIRST-27. Generate against contracts, and turn every reliance on a body into a finding.**
Generating agents build against the real `flor` — a git dependency checks out its whole tree, bodies and suite included — and are instructed to code against each unit's public API and documentation. Reading a body is not forbidden; relying on what a contract does not state is reported instead: wherever generated code depends on behaviour the contract leaves unsaid, however the agent learned it, the agent files a finding. A contract may still be tagged before its body exists — a crate whose functions are unimplemented still yields a complete interface — so SD generates against a frozen contract while DD fills it in, and only the assembly move waits for a working implementation.
*Because* an agent that relies on a body codes against observed behaviour rather than against the contract, and the invariants it picks up that way become load-bearing without being written down — the coupling the contracts exist to prevent, and one that surfaces as a silent break the next time DD refactors.
*Because* that coupling forms where a contract is silent: an agent reads a body exactly when the interface does not answer its question, so what does the damage is less the reading than the gap it closes without anyone learning of it. Reported, the reliance is a finding (AIFIRST-19) and the contract improves; unreported, a gap in the corpus is papered over.
*Because* keeping bodies out mechanically is not a boundary worth holding. `flor` is public and every build of `flor-dist` checks it out, so an environment airtight against it must also give up the web, local runs against the reviewed crates, and the upstream material generation draws on — and the gain would stay partial even then, since an agent that runs the product observes behaviour through the interface whether or not it reads a body.
*Accepting* that the boundary is held by instruction and audited after the fact rather than prevented: what an agent opened is in its transcript.
*Accepting* that the suite is reachable the same way, since it sits in the same tree, so AIFIRST-28 is held by the same instruction and the same audit.
*Rejected* building generation against interface-only stand-ins of `flor`, in an environment with no route to it — mechanical, at the price of an extractor to maintain, no local run of any reviewed path, and an environment cut off from the web, for a gain black-box observation erodes anyway.
*Rejected* a separate contracts repository — it splits a contract from its implementation across repositories, multiplying the cost of the early API churn that AIFIRST-09 deliberately front-loads. *Rejected* `<unit>-api` interface crates — the standard Rust shape, but it re-expresses a contract as traits and forces indirection at every call site, to buy a mechanical isolation this model has chosen not to pay for.

### Change and substitution

**AIFIRST-13. Substitute by a fixed sequence, deleting the SD implementation last.**
Freeze the unit's contract; have `flor-dist` build a second configuration taking the DD crate by git tag; require the suite green in both configurations; land the assembly move; then delete the SD implementation.
*Because* deleting last keeps every earlier step reversible by the same one-line change, and running both configurations catches a DD crate that passes on its own terms while changing behaviour the product depends on.
*Because* the suite is black-box over the product, not individual crates.
*Rejected* substituting automatically on a DD release — it couples a release decision to a product decision and removes the human from a change that reaches customers.

**AIFIRST-14. Hold the conformance suite in `flor`, append-only, and run it from `flor-dist`.**
The suite is black-box and implementation-independent, human-owned, never regenerated. It holds two kinds of test: **conformance tests**, written against a contract, saying what the product promises; and **regression tests**, one per defect found, saying what it once got wrong. `flor-dist`'s CI executes both, since only it builds the product, in both configurations during a substitution window. A component's own unit tests are not part of the suite and are regenerated with the component.
*Because* a regenerated component returns with different bugs, and the accumulated capture of every bug already found is the only thing between that and a customer.
*Because* the same suite must be green on both sides of a substitution, so it can belong to neither implementation.
*Accepting* that it grows monotonically and gets slow.
*Rejected* pruning it — a test is amended, or where a design deliberately drops the behaviour it covers removed outright, but either way traceably to the decision that did it, since append-only decays one undocumented exception at a time. What is refused is deletion because a test is inconvenient, slow or failing.

**AIFIRST-28. Keep the suite a gate at generation and an input at patching.**
The generating agent does not read the suite. It reads the corpus, and afterwards the suite judges what it produced; only once a test fails does that test become input, which is the patching rule already. The one part visible throughout is a **defect ledger** — one human-written line per captured defect, no assertions and no fixtures — so a fresh implementation can avoid the known traps without seeing the oracle.
*Because* an implementation generated to satisfy an append-only suite converges toward the implementations whose defects filled it, which is the opposite of coming back different — and where the suite is silent the agent fills the gap arbitrarily, while a wrong test simply becomes the specification with nothing pushing back.
*Because* a failure then carries information: either the agent misread the corpus, or the corpus and the suite disagree. Read as a finding, that is the reality check SD exists to provide.
*Because* a conformance test's obligation belongs in the corpus in any case — the test is the executable form of a promise, not a new requirement — so a test whose obligation cannot be derived from the corpus is a gap in the corpus rather than a rule hidden from the line that has to satisfy it.
*Accepting* a patching phase after every generation, paid in tokens and wall-clock, where showing the suite would have bought a faster first green.
*Revisit* at A0, which is where the two costs can be compared for real. The recorded fallback is to expose the suite at generation and accept the convergence, and the ledger is what would stay either way.

**AIFIRST-15. Split the human loop by property and by API.**
Humans own scope, acceptance criteria, failure-mode enumeration, the security boundary, the suite, the runbook, and every contracted unit's public API. On DD they also own structure, naming and diff review. On SD they own none of those, and no generated code is reviewed.
*Because* the properties agents fail at do not fail together: happy-path correctness is good, evolvability is deliberately sacrificed, and failure-path and security correctness are weak.
*Because* what an edit drops is what nothing else catches: an agent can delete the line that verifies something and leave every test passing, and on a line nobody reads that goes unnoticed. Diff review is the only check against an omission, which is why DD has it and why a unit whose omissions would be a breach is DD-authored.
*Accepting* that this is the model's largest recurring human cost.

**AIFIRST-16. Regenerate the unit; patch only behind a failing suite test.**
The unit of change on SD is the unit, regenerated from the corpus — from whatever context the agent gathers, no page map. A patch is admissible only once a failing conformance-suite test exists. A defect invisible at the suite's altitude may be fixed against the component's own tests, and is understood to be discarded at the next regeneration.
*Because* admissibility must be decidable without reading the code, and a failing test is an objective trigger.
*Because* a fix justified only by a unit test loses its justification at the next regeneration, and goes with it.

**AIFIRST-17. Regenerate on a defect ceiling, a contract change or a scope shift.**
Any of the three triggers a regeneration: fixes reliably producing new defects, a contract the implementation behind it cannot absorb, or a milestone whose requirements diverge enough that adapting costs more than generating.
*Because* all three are visible from outside the code, and the append-only suite makes any of them safe to act on.
*Accepting* that the defect ceiling is noisy and its first firing is a judgement rather than a threshold crossing.

**AIFIRST-18. Choose what moves DD-ward by trigger, and report the share.**
Movement is triggered by the threat-model pass or the defect ceiling, never by quota. Among triggered candidates, severity decides and shape breaks ties — data-shaped units substitute into any consumer, lifecycle-shaped ones impose a runtime. A unit may move once everything it depends on is contracted, not once its dependencies are DD-authored. Each release reports the DD-authored share of units, which units moved since the last release, and how much of the security-relevant surface that share covers.
*Because* the failure mode is a frontier that never advances, and reporting what moved makes that visible without dictating a response.
*Because* a bare share would not show it: we define the units it counts, so a re-decomposition moves the ratio without moving any implementation.
*Rejected* a fixed effort split — it converts judgement into arithmetic and will be gamed by whoever is behind on it.

### Findings and public posture

**AIFIRST-19. Route findings and conflicts through a design pass.**
What SD learns is filed against the corpus and enters through a design pass, never as a direct amendment. Where SD's working behaviour contradicts a corpus decision, neither side wins automatically: the conflict is such a finding, carrying the deployed behaviour as a fact rather than a proposal. A contract is corpus (AIFIRST-26), so this covers contracts too: an agent that finds a unit's API wrong or missing something proposes the change as a finding, and a human takes it through the pass. Wanting a different contract is one of the more useful things generation can report, and it is still not a licence to write one.
*Because* an amendment made under release pressure is a design decision taken without the gates, and that is how the corpus stops being the shared upstream.
*Because* a corpus decision may be wrong — the reality check SD exists to provide — and SD may simply have improvised. Nothing about the conflict itself says which.

**AIFIRST-20. Publish both repositories; accept contributions only to `flor`.**
`flor` is open to contribution. `flor-dist` is public for customer due diligence but read-only: a defect there is reported as a failing suite test against `flor`.
*Because* a patch to SD would be discarded at the next regeneration, wasting the contributor's work, while a test survives every future implementation of that unit.
*Accepting* that a public repository refusing patches must say so plainly, or every drive-by pull request is a small betrayal.

**AIFIRST-21. State provenance as the engineering model, not as an AI disclosure.**
The repositories and the product documentation describe the model and its current state, including the DD-authored share. Version output and release notes carry none of it.
*Because* "parts of this are AI-generated" is the sentence a slop project also writes, so as a disclosure it carries no information. The discriminating claim is that the boundaries are human-owned and the units are being replaced by reviewed implementations, which no vibe-coded product can say.

### Releases, assurance and cadence

**AIFIRST-22. Give every release a note naming its audience and its promise, and promise support rather than availability.**
Each release states who it is for, what it does and does not do, and what is promised. Early milestones are testbed and dogfooding artifacts and say so. All users get a supported-version window and security advisories. Paying customers get a response time and a fix turnaround.
*Because* "release" implies usability and support, and a milestone that sells nothing must say so or the word does the lying.
*Because* through the C line the software runs on the customer's own premises, so an availability guarantee would cover things we neither control nor can measure.

**AIFIRST-23. Version verbatim from 1.0.0 at A0; candidates carry `-rc.N`.**
Nothing is released before A0, so pre-A0 builds carry `0.x` and no promise. A0 is 1.0.0 and semver applies verbatim from there; a milestone usually breaks compatibility and so usually takes a major. A candidate is `X.Y.Z-rc.N`, promoted to `X.Y.Z` once the test environment approves (by rebuilding at the release version), and an `-rc` build is not a release and carries no note. DD unit crates stay in `0.x`.
*Because* below 1.0 there is no position for a breaking change, and the convention that fills that gap is the one Cargo already implements for `0.x`.
*Because* pre-release identifiers sort correctly and are not selected without an explicit opt-in.
*Accepting* that majors climb roughly one per milestone, which reads as instability because it is.
*Revisit* a stable-versus-rc channel in the installer, which ships the binaries and where the resolver's semantics do not apply.

**AIFIRST-24. Security-audit each milestone's released product, and independently before customers.**
Every milestone gets a security audit of what it releases: a human threat-model pass over the whole product, DD-authored units included, and an AI-assisted code audit of it, run by a different agent than the one that generated it. An independent third-party audit precedes the first customer milestone; where it cannot be, the release states that limitation instead of shipping quietly.
*Because* the contracted units cover the crypto core but not the surfaces reaching it — e.g. parsers, the forwarding engine, the artifact applier.
*Because* an author cannot audit their own foundations: knowing the intended invariants is precisely what an auditor must not assume, which is a context problem rather than a skill one.
*Because* a generator and an auditor sharing a model share blind spots, so the audit would confirm the assumptions that produced the defect.

**AIFIRST-25. Do DD work in the gap after a release.**
*Because* scheduling DD alongside SD puts them in competition for the core team, which SD wins every time — it has customers where DD has principles.
*Accepting* that a release with a long defect tail eats its own gap, which is exactly when a unit most needs moving.
